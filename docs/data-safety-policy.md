# Data Safety Policy

이 앱의 사용자 데이터 변경은 반드시 API/CRUD 계층을 통과해야 한다. 직접 DB 커밋, UI별 부분 객체 저장, 기본값 기반 전체 덮어쓰기는 설정 증발의 재발 원인이므로 금지한다.

## 필수 원칙

1. **저장 계약 동기화**: 다이얼로그/런타임 모델에 있는 설정은 `GlobalSettings` DB 모델, API schema, 자동 마이그레이션에 모두 존재해야 한다.
2. **부분 변경 우선**: 일부 설정만 바꾸는 화면은 `patch_settings()`로 변경 필드만 저장한다.
3. **actor 기반 허용 범위**: 설정 저장은 `X-HH-Beholder-Actor` 또는 CRUD actor로 출처를 남기고, 해당 화면에서 수정 가능한 필드만 허용한다.
4. **커밋 전 백업**: `global_settings`, `managed_processes`, `web_shortcuts`, `process_sessions` 변경 전에는 JSON snapshot을 남긴다.
5. **비홀더 선차단**: 대량 기본값 회귀, 허용 범위 밖 컬럼 변경, 중복 open session, 열린 세션이 있는 게임 삭제, 비정상 기록값 등은 commit 전에 incident로 차단한다.
6. **사용자 결정 우선**: 비홀더는 안전한 권장안을 제시하되, 세션 병합/닫고 새로 시작/기록 닫고 삭제 같은 스마트 조치는 사용자가 선택해야 실행한다.
7. **라우터 직접 커밋 금지**: FastAPI/PySide6 경로는 `db.commit()`을 직접 호출하지 말고 CRUD/Beholder 함수로 위임한다. Beholder 내부 incident 처리와 CRUD 내부 커밋만 예외다.

## 구현 체크리스트

- 새 설정 추가 시: DB column + schema field + runtime data model + migration + preservation test.
- 새 저장 화면 추가 시: actor 이름 + 허용 필드 집합 + 설정 보존 회귀 테스트.
- 새 DB write 추가 시: CRUD 함수에서 `BeholderOperation`을 만들고 직접 `db.commit()`을 UI/router에 두지 않는다.
- 중요 테이블 변경 시: 변경 전 snapshot을 `backups/settings` 또는 `backups/mutations/<table>`에 남긴다.
- incident UX 추가 시: `user_title`, `user_summary`, `user_impact`, `available_actions`를 함께 제공한다.

## 장애 DB의 복구 접근과 완료

API 생존과 정상 DB 준비는 별개다. 기존 ping은 서버 생존을, health의 db_ready와
database_access는 일반 데이터 사용 가능 여부를 소유한다. fault 상태에서도 백업 목록·
미리보기·복구 API와 복구 화면에 접근할 수 있어야 한다. 일반 데이터 관리자·모니터·출석·
스케줄러는 검증된 복구와 앱 재시작 전에는 시작하지 않는다.

유지보수 context 종료나 HTTP 오류 응답은 복구 성공이 아니다. 기본 종료는 진입 전
상태로 돌아가며, 새 DB 적용·검증 성공을 명시한 때만 fault 표시와 일반 쓰기 차단을
해제한다. 취소·교체 전 실패·복구/롤백 실패·안전 상태 해제 실패에서는 보호를 유지한다.
정상 상태의 교체가 실패하고 정상 원본이 유지되면 기존 정상 상태로 돌아간다.

정상 DB 교체는 검증된 SQLite snapshot과 rollback을 유지한다. 손상 DB 복구는 원본 DB와
존재하는 WAL·SHM을 먼저 보존하되 원본의 SQLite 무결성을 복구 선행 조건으로 요구하지
않는다. 보존·연결 정리가 실패하면 교체하지 않는다. 손상 원본 rollback은 fault 상태를
유지한다. 사용자 데이터 대신 격리 DB로 손상·부분 실패·재시작·복구 재시도를 검증한다.

## 게임 정체성과 종료 후 자원 추적

등록 ID는 같은 게임 주체와 누적 기록을 소유한다. 감시 경로는 그 게임을 찾는 위치다.
같은 ID의 경로 수정은 다른 게임을 뜻하지 않으며 진행 중 관측도 같은 게임에 수용한다.
개별 OS 실행 인스턴스의 시작·종료와 게임 기록의 정체성은 구분한다.

종료 기록 저장 성공 후 (게임 ID, 종료 세션 ID)별 follow-up을 등록한다. 등록부터 180초
동안 등록 직후·60초·120초에 조회를 시도하고 180초부터 신규 조회를 시작하지 않는다.
놓친 슬롯을 기간 밖에서 몰아 실행하지 않는다. 시작한 요청은 기존 timeout 내에서
응답과 저장까지 완료한다. 재실행·추가 종료·동일 응답·안정화는 취소나 조기 종료 사유가
아니다. 앱 종료·등록 삭제·제공자/계정 변경은 해당 입력의 작업을 종료한다.

각 성공 응답은 기존 자연 회복량 계산으로 **그 작업의 종료 시각으로 역산**하여 해당
세션의 종료값을 보정한다. 재실행 후 소비 등 변화 원인을 분류하거나 보정을 제한하지
않는다. 실패는 이전 성공값을 지우지 않으며 현재 자원 저장과 종료 세션 보정의 결과를
각각 기록한다. 한쪽 실패를 다른 쪽 성공으로 표시하거나 성공한 저장을 되돌리지 않는다.

저장형 수동·시작·종료 조회는 기존 제공자별 직렬 실행 경계에서 조회와 저장을 한 작업으로
완료한다. 현재 자원의 DB writer는 조회 시점 예상값과 응답을 비교한다. HoYo는 정수,
NIKKE는 소수 첫째 자리로 비교하여 같으면 기준값·회복 기준 시각을 유지하고 다르면
새 관측을 적용한다. 최대값·상태·라벨 변경은 타이머 변경과 구분한다.

기존 자원 PATCH 입력의 시각은 관측 시각이고 반환 행의 updated_at은 실제 회복 기준
시각이다. GUI는 저장 결과를 사용하고 요청 값으로 로컬 타이머를 먼저 덮어쓰지 않는다.
일반 등록 편집은 최신 런타임 필드를 보존한다. 별도 관측 시각 DB 필드·자원 저장소는 없다.
