# Data Safety Policy

이 앱의 사용자 데이터 변경은 반드시 API/CRUD 계층을 통과해야 한다. 직접 DB 커밋, UI별 부분 객체 저장, 기본값 기반 전체 덮어쓰기는 설정 증발의 재발 원인이므로 금지한다.

현재 앱의 데이터 접근은 `ApiClient → API → CRUD/Beholder` 경계를 따른다. 별도 JSON 저장용
DataManager나 GUI-side SchemaMigrator를 병렬로 유지하지 않는다. DB 생성·검증·마이그레이션은
기존 DB 초기화 경로가 소유하며, 과거 로컬 JSON 파일을 정리 목적으로 임의 삭제하지 않는다.

## 필수 원칙

1. **저장 계약 동기화**: 다이얼로그/런타임 모델에 있는 설정은 `GlobalSettings` DB 모델, API schema, 자동 마이그레이션에 모두 존재해야 한다.
2. **부분 변경 우선**: 일부 설정만 바꾸는 화면은 `patch_settings()`로 변경 필드만 저장한다.
3. **actor 기반 허용 범위**: 설정 저장은 `X-HH-Beholder-Actor` 또는 CRUD actor로 출처를 남기고, 해당 화면에서 수정 가능한 필드만 허용한다.
4. **커밋 전 백업**: `global_settings`, `managed_processes`, `web_shortcuts`, `process_sessions` 변경 전에는 JSON snapshot을 남긴다.
5. **비홀더 선차단**: 대량 기본값 회귀, 허용 범위 밖 컬럼 변경, 중복 open session, 열린 세션이 있는 게임 삭제, 비정상 기록값 등은 commit 전에 incident로 차단한다.
   OBS 연동의 녹화 사용·최소화 실행·녹화 파일 표시·홀드 시간과 사이드바 손잡이 자동 숨김은
   되돌릴 수 있는 앱 동작 선택이다. 이 항목들을 개별 기본값 회귀로 차단하지 않는다. actor/허용 필드, 값 범위,
   저장 전 스냅샷과 대량 기본값 회귀 검사는 그대로 적용한다. OBS 권위 값과 앱 선택의
   구분은 [Windows 호스트 계약](development/windows-host-lifecycle.md)을 따른다.
6. **사용자 결정 우선**: 비홀더는 안전한 권장안을 제시하되, 세션 병합/닫고 새로 시작/기록 닫고 삭제 같은 스마트 조치는 사용자가 선택해야 실행한다.
7. **라우터 직접 커밋 금지**: FastAPI/PySide6 경로는 `db.commit()`을 직접 호출하지 말고 CRUD/Beholder 함수로 위임한다. Beholder 내부 incident 처리와 CRUD 내부 커밋만 예외다.

## 구현 체크리스트

- 새 설정 추가 시: DB column + schema field + runtime data model + migration + preservation test.
- 새 저장 화면 추가 시: actor 이름 + 허용 필드 집합 + 설정 보존 회귀 테스트.
- 새 DB write 추가 시: CRUD 함수에서 `BeholderOperation`을 만들고 직접 `db.commit()`을 UI/router에 두지 않는다.
- 중요 테이블 변경 시: 변경 전 snapshot을 `backups/settings` 또는 `backups/mutations/<table>`에 남긴다.
- incident UX 추가 시: `user_title`, `user_summary`, `user_impact`, `available_actions`를 함께 제공한다.

## 장애 DB의 복구 접근과 완료

기존 DB는 읽기 전용 무결성 검사를 통과한 뒤에만 백업·마이그레이션·일반 초기화를
수행한다. 검사 실패는 기존 fault 보호 상태로 전환하고 복구 API를 유지한다. 자동 백업은
새 임시 snapshot 생성과 무결성 검증을 마친 뒤 기존 슬롯을 회전한다. 손상 DB의 반복
실행이나 새 백업 실패가 정상 백업을 삭제해서는 안 된다.

복구 API는 GUI의 `prepare_database_restore` IPC 완료를 확인한 뒤 교체한다. GUI는
기존 2초 정리 제한으로 일반 writer와 외부 조회 작업을 중지하고 완료 때만 ACK한다.
IPC 대기는 5초이며 살아 있는 GUI의 불통·중지 실패는 교체 전 실패다. 준비한 GUI는
재시작 전 일반 작업을 재개하지 않는다. 복구 HTTP 요청은 GUI 스레드 밖에서 실행하여
IPC 처리를 막지 않는다. 서버 전용 실행은 기존 부모 프로세스 정보로 구분한다.

API 생존과 정상 DB 준비는 별개다. 기존 ping은 서버 생존을, health의 db_ready와
database_access는 일반 데이터 사용 가능 여부를 소유한다. fault 상태에서도 백업 목록·
미리보기·복구 API와 복구 화면에 접근할 수 있어야 한다. 일반 데이터 관리자·모니터·출석·
스케줄러는 검증된 복구와 앱 재시작 전에는 시작하지 않는다.

유지보수 context 종료나 HTTP 오류 응답은 복구 성공이 아니다. 기본 종료는 진입 전
상태로 돌아가며, 새 DB 적용·검증 성공을 명시한 때만 fault 표시와 일반 쓰기 차단을
해제한다. 취소·교체 전 실패·복구/롤백 실패·안전 상태 해제 실패에서는 보호를 유지한다.
정상 상태의 교체가 실패하고 정상 원본이 유지되면 기존 정상 상태로 돌아간다.

정상 DB 교체는 검증된 SQLite snapshot과 rollback을 유지한다. 손상 DB 복구는 원본 DB와
존재하는 WAL·SHM을 먼저 보존하되 원본의 SQLite 무결성을 복구 선행 조건으로 요구하지
않는다. 보존·연결 정리가 실패하면 교체하지 않는다. 손상 원본 rollback은 fault 상태를
유지한다. 사용자 데이터 대신 격리 DB로 손상·부분 실패·재시작·복구 재시도를 검증한다.

## 게임 정체성과 종료 후 자원 추적

등록 ID는 같은 게임 주체와 누적 기록을 소유한다. 감시 경로는 그 게임을 찾는 위치다.
같은 ID의 경로 수정은 다른 게임을 뜻하지 않으며 진행 중 관측도 같은 게임에 수용한다.
개별 OS 실행 인스턴스의 시작·종료와 게임 기록의 정체성은 구분한다.

실패한 프로세스 관측으로 종료 기록을 만들거나 실행 중인 상태를 지우지 않는다. 시작 시
열린 기록 점검이 성공한 뒤 정상 감시와 heartbeat를 시작한다. 연결·작업 재시도와 수명주기
완료 계약은 [Windows 호스트 계약](development/windows-host-lifecycle.md)을 따른다.

종료 기록 저장 성공 후 (게임 ID, 종료 세션 ID)별 follow-up을 등록한다. 추적 기간은
저장·등록 시각이 아닌 **실제 종료 시각부터 600초**다. 종료 기준 0·60·120·…·540초의
고정 슬롯에 조회를 시도하며 600초부터 새 제공자 조회를 시작하지 않는다. 저장이 늦게
끝나면 남은 기간 안에서 즉시 한 번 조회한 뒤 다음 고정 슬롯으로 이어 간다. 누락된
슬롯을 모아 실행하거나 늦은 등록으로 추적 기간을 늘리지 않는다. 재실행·추가 종료·
동일 응답·안정화는 취소나 조기 종료 사유가 아니다. 앱 종료·등록 삭제·제공자/계정
변경은 해당 입력의 작업을 종료한다.

종료 기록 저장과 last_played 갱신은 별개의 결과다. 종료가 저장되면 부가 저장 실패에도
follow-up을 등록한다. 부가 저장 재시도는 종료 기록이나 follow-up을 중복 생성하지 않는다.

종료 후 600초 안에 **실제 제공자 조회를 시작한 요청**만 현재 자원과 고정 대상 세션의
종료값을 함께 갱신할 수 있다. 요청을 큐에 넣은 시각이나 호출자가 전달한 시각으로
권한을 만들지 않는다. API가 DB의 종료 세션·등록 대상·계정을 확인하고 제공자 조회부터
저장까지 소유한다. 기간 안에 시작한 조회는 응답·저장이 기간 밖에서 끝나도 보정할 수
있다. 기간 뒤에 시작하는 조회와 임의 값 PATCH는 종료 세션을 보정할 수 없다.

성공 응답은 자원 단위별 자연 회복량을 **그 작업의 종료 시각으로 역산**하여 해당 세션의
종료값을 보정한다. 정수로 회복하는 자원은 완전히 지난 회복 주기의 수량을 빼고, 명조는
그 수량을 최대치에 대한 비율로 환산해 기존 `resource_percent_at_end`에 기록한다.
겹치는 종료 작업은 감지 시점의 조회 대상과 각자의 종료 시각·세션 ID를 유지한다.
재실행 후 소비 등 변화 원인은 분류하지
않는다. 실패는 이전 성공값을 지우지 않으며 현재 자원 저장과 종료 세션 보정의 결과를
각각 기록한다. 한쪽 실패를 다른 쪽 성공으로 표시하거나 성공한 저장을 되돌리지 않는다.

주기 서버 모니터링은 한국 표준시(KST) 매시 00분·30분에 지원하는 등록 게임의 **현재
자원만** 조회한다. 계속 실행 중인 호스트는 하루 48회차를 처리하며, 앱 기동 시각을
기준으로 간격을 세거나 놓친 회차를 모아 실행하지 않는다. 기존 1초 스케줄러가 해당
00분·30분의 60초 안에 도달했을 때 회차당 한 번 실행하고, 기동한 현재 회차는 기존
기동 조회가 소유한다. 시작·기동·수동 조회도 현재
자원만 갱신하며 종료 세션에는 쓰지 않는다.

게임 종료를 감지한 순간부터 600초 동안은 해당 게임의 주기 회차를 건너뛴다. 종료 저장
대기·실패도 이 제외 기간을 연장하거나 없애지 않는다. 다른 게임과 시작·기동·수동 조회는
계속 허용한다. 예를 들어 10:25 종료이면 10:30 회차를 생략하고 10:35에 보충하지 않으며
다음 정기 조회는 11:00이다. 대기 중인 주기 조회는 GUI 작업 큐에서 **API 관측 호출을
시작하기 직전** 종료 여부를 다시 확인한다. 이미 API 관측 호출을 시작한 현재 자원 전용
요청은 그 뒤 종료를 감지해도 완료할 수 있으며 세션 보정 권한을 얻지 않는다. 이 경계는
종료 세션 보정 권한을 판정하는 실제 제공자 HTTP 조회 시작 시각과 구분한다.
만료 후 남아 있는 요청의 응답을 기다리는 동안에도 주기 제외 기간을 늘리지 않는다.

저장형 수동·시작·기동·주기·종료 조회는 기존 제공자별 직렬 실행 경계에서 조회와 저장을 한 작업으로
완료한다. 현재 자원의 DB writer는 조회 시점 예상값과 응답을 비교한다. 정수 자원은 수량,
NIKKE는 소수 첫째 자리로 비교하여 같으면 기준값·회복 기준 시각을 유지하고 다르면
새 관측을 적용한다. 최대값·상태·라벨 변경은 타이머 변경과 구분한다.

현재 자원 관측의 입력 시각은 관측 시각이고 반환 행의 updated_at은 해당 자원의 회복 기준
시각이다. 이 값은 마지막 조회 시각이나 주기 회차의 기준이 아니다. GUI는 저장 결과를
사용하고 요청 값으로 로컬 타이머를 먼저 덮어쓰지 않는다.
일반 등록 편집은 최신 런타임 필드를 보존한다. 별도 관측 시각 DB 필드·자원 저장소는 없다.

신규 등록, 추적 활성화 또는 제공자·추적 대상 변경이 저장되면 서버가 확정한 등록 ID로
현재 자원을 한 번 조회한다. 미저장 조회 테스트 값은 저장하지 않으며, 같은 대상의 일반
편집은 불필요한 조회 없이 최신 관측을 유지한다. 이 첫 조회는 종료 세션을 보정하지 않는다.

### 일반·저장 자원의 값과 표시

명조의 일반 현재량·최대치와 저장 현재량·최대치는 Process의 `resource_current`,
`resource_max`, `resource_reserve_current`, `resource_reserve_max` 네 수량이 소유한다.
수량형 자원의 DB `resource_percent`는 비워 두고 비율은 읽을 때 계산한다. 제공자의 조회
결과는 공용 관측 입력으로 변환하고, 표시와 종료 보정은 자원 단위와 회복 규칙을 사용한다.
명조는 `resource_updated_at`의 기준 수량에서 6분마다 일반 플레이트 1개가 회복된 것으로
계산하여 게이지와 완료 예상 시각을 표시한다. 실제 회복 주기에서 이미 지난 시간이
기록되지 않으므로 예상 시각은 최대 한 회복 주기까지 늦을 수 있고, 관측 뒤 자원을
사용하면 오차가 커질 수 있다. 예비 플레이트는 서버 관측 수량을 표시한다.
기존 HoYo의 `stamina_current`·`stamina_max`와 NIKKE의 비율 저장 권위는 유지한다.

스타레일의 저장량은 서버의 `current_reserve_stamina`를 사용하며, 상한은
[공식 예비 개척력 안내](https://www.hoyolab.com/article/21174438)의 2,400이다.
초과 수량을 제공하지 않는 응답은 `None`으로 구분하고 0이나 추정 수량을 만들지 않는다.
새 성공 관측에서 초과 필드가 빠지면 이전 관측의 초과량을 섞지 않고 해당 값을 비운다.
조회 자체가 실패하면 이전 성공 수량을 보존한다. 모든 수량은 기존 관측 API와
CRUD/Beholder writer를 통과하며 일반 등록 편집이 덮어쓰지 않는다.

메인·사이드바·API의 표시값은 저장 수량에서 공용 순수 계산으로 만든다. 표시 여부는
저장 수량을 삭제하지 않으며, 겹침과 숫자 선택은 [GUI 표시 계약](development/windows-gui-modernization.md#사이드바-표시-계약)이 소유한다.

자원 연동의 계정 연결·변경·해제는 자원/출석 관리가 소유하고, 게임 편집은 추적 사용 여부와
추적할 자원만 저장한다. 명조의 선택 계정은 제공자 설정 `wuwa_link.json`의
`selected_resource_key` 한 곳에서 보존하며, 게임의 `resource_key`에는 자원 종류인
`waveplate`만 저장한다. 연결 해제는 선택값 `null`로 보존하고 공식 런처의 로그인은 유지한다.
인증값은 공식 Windows 런처 캐시에서 메모리로만 읽고 별도 토큰 저장소로 복사하지 않는다.
계정 확인은 설정을 바꾸지 않으며, 여러 유효 계정 중 대상을 캐시 순서로 임의 선택하지 않는다.

이전 게임 데이터의 계정 선택은 명시적인 초기화·복구 writer에서 제공자 설정으로 옮긴다.
선택이 하나로 확정될 때만 자동 이동하며, 이미 저장된 해제 선택을 다시 연결하지 않는다.
게임 ID·추적 사용 여부·기존 세션 기록은 보존하고, 이전 계정의 현재 자원은 새 계정의 값과
섞지 않는다. 연결 변경·해제 시 이전 계정 작업을 취소하며 늦은 응답도 저장하지 않는다.
연결 확정 후 추적 중인 게임은 공통 현재 자원 조회를 시작하고 게임 편집 재저장을 요구하지 않는다.
`queryPlayerInfo`의 계정 준비는 세션 보정 권한을 만들지 않는다. `queryRole`의 자료 준비 중
응답(1005)만 0.5초 뒤 재조회하며 각 요청 종류당 최대 5회로 제한한다. 재조회마다 실제
요청 시작 시점의 취소·대상·600초 권한을 다시 확인하며 이전 요청의 권한을 넘겨받지 않는다.
